# libmpv: свои FFI-объявления и сборка LGPL

Почему у LimeKit собственные объявления функций libmpv вместо готового
Rust-крейта, откуда берётся `libmpv-2.dll` и какие опции плеера важны для обоев.

## Свой тонкий FFI вместо `libmpv2`

| Вариант | Лицензия | Решение |
|---|---|---|
| `libmpv2` (форк libmpv-rs) | LGPL-2.1 | не взял |
| `libmpv-rs` | LGPL-2.1 | не взял |
| свои объявления | GPL-3.0, как весь LimeKit | **выбрал** |

`crates/mpv` объявляет около полутора десятков функций документированного C API
(v2.x) и render API. Объявления написаны по официальной документации, заголовки
mpv не копировались. Сама библиотека загружается в рантайме через `libloading`.

Что это даёт:

- рендерер собирается без `libmpv-2.dll`, без import-lib и без зависимости на
  этапе линковки;
- dll лежит рядом с программой и заменяется пользователем, а именно этого LGPL
  требует от того, кто её распространяет;
- отсутствующая или битая dll даёт обычную ошибку при загрузке: все символы
  разрешаются сразу, а не при первом вызове.

Цена: API mpv я поддерживаю сам. При обновлении библиотеки нужно сверять
объявления с документацией, а на macOS, где `--wid` не работает, понадобится
весь render API.

## Откуда `libmpv-2.dll`

- Популярные сборки (shinchiro и зеркала) собраны под GPLv3 со всеми
  кодеками, это больше, чем нужно.
- mpv собирается в режиме LGPL опцией meson `-Dgpl=false`. ffmpeg внутри тоже
  должен быть в конфигурации LGPL, без libx264 и подобного. Для
  воспроизведения нужны только декодеры.
- Сейчас LimeKit берёт артефакт `mpv-dev-lgpl-x86_64` из
  [zhongfly/mpv-winbuild](https://github.com/zhongfly/mpv-winbuild): это
  ежедневные сборки в GitHub Actions с открытыми логами. Версия и SHA-256
  закреплены в [docs/third-party.md](../third-party.md), скачивает
  `scripts/fetch-libmpv.ps1`.
- Мейнтейнер этих сборок прямо пишет, что не даёт юридических гарантий их
  состава. Надёжнее собирать mpv в своём CI с той же конфигурацией, это
  следующий шаг.

## Опции плеера

Проверено на Windows 10 22H2.

- До `mpv_initialize` задаются: `wid` (окно поверхности), `hwdec=auto-safe`,
  `loop-file=inf`, `image-display-duration=inf` (картинки идут тем же путём, что
  видео), `panscan=1.0` (заполнить экран без полос), `border=no` (без него на
  24H2 появляется рамка), `stop-screensaver=no`, `input-default-bindings=no`,
  `osd-level=0`, `load-scripts=no`, `config=no`.
- `hwdec-current` появляется не сразу, его нужно спрашивать после начала
  декодирования. Для H.264 и HEVC 1080p это `d3d11va`, процессор в отладочной
  сборке занят на 1,5–5%.
- `pause=true` действительно останавливает декодирование: 0% процессора.
- Статичная картинка (Motion JPEG 4K) после первого кадра тоже даёт 0%.
- FSR подключается в рантайме свойством `glsl-shaders` (путь с прямыми
  слэшами) и только когда исходник меньше монитора.
- Если сторож пересоздал окно поверхности, например после перезапуска
  Проводника, старый `wid` указывает на уничтоженное окно. Веб-поверхности
  сторож пересобирает сам. Что в этот момент происходит с видео, пока не
  проверено, это одна из открытых строк в [workerw.md](workerw.md).
